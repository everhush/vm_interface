# Native offline disk export

Prepared for KubeVirt 1.9's native VirtualMachineExport v1 path. The API accepts only independent data disks belonging to the authenticated account and a stopped VM whose lifecycle has converged. It validates the populated CDI DataVolume and PVC UIDs, reserves a single export per VM, uses a fixed internal TLS endpoint and only the native raw image format, and streams no more than the reserved disk capacity. Export TTL is 15 minutes; clients should explicitly close the export and wait for deletion before resuming writes. The dedicated export secret is generated by the operator at cluster setup, never returned to API callers, and not readable by the service account through Kubernetes RBAC. Admission constrains source names, owner and secret reference; exporter ingress is restricted to the API pod and egress is denied. This is a disposable single-namespace profile; the shared internal export token is not a public or per-account credential. Do not expose the KubeVirt export proxy externally.

The integration test uploads a known raw fixture, checks its verified digest, creates an offline export, tests cross-account denial and start interlock, streams the full output with client SHA256 and checks actual prefix bytes, then closes it. Native export conformance is pending until this test actually passes.

Larger cold clone is not in-place PVC or guest filesystem growth. The current K3s local-path profile does not establish expansion-capable CSI behavior. In-place growth, guest partition/filesystem expansion, qualified snapshot/restore and system/exchange export remain separate requirements; do not advertise these as implemented or certified.
