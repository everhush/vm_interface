# Native offline disk export

Prepared for KubeVirt 1.9's native VirtualMachineExport v1 path. The API accepts independent data disks and the reserved `system.disk` and `exchange.disk` (block exchange only) selectors belonging to the authenticated account and a stopped VM whose lifecycle has converged. It validates the populated CDI DataVolume and PVC UIDs, reserves a single export per VM, uses a fixed internal TLS endpoint and only the native raw image format, and streams no more than the reserved disk capacity. Export TTL is 15 minutes; clients should explicitly close the export and wait for deletion before resuming writes. The dedicated export secret is generated by the operator at cluster setup, never returned to API callers, and not readable by the service account through Kubernetes RBAC. Admission constrains source names, owner and secret reference; exporter ingress is restricted to the API pod and egress is denied. This is a disposable single-namespace profile; the shared internal export token is not a public or per-account credential. Do not expose the KubeVirt export proxy externally.

The integration test uploads a known raw fixture, checks its verified digest, creates an offline export, tests cross-account denial and start interlock, streams the full output with client SHA256 and checks actual prefix bytes, then closes it. This native export integration stage passed on the migrated candidate in [46077980605](https://github.com/everhush/vm_interface/actions/runs/46077980605). Full core qualification and independent artifact review remain pending; prior qualification is historical. See [migration record](toolchain-migration.md) and [validation.md](validation.md).

Larger cold clone is not in-place PVC or guest filesystem growth. The current K3s local-path profile does not establish expansion-capable CSI behavior. In-place growth, guest partition/filesystem expansion, qualified snapshot/restore and a complete VirtioFS filesystem backup/restore remain separate requirements; do not advertise these as implemented or certified.

Sources: https://github.com/kubevirt/kubevirt/blob/v1.9.0/staging/src/kubevirt.io/api/export/v1/types.go and https://github.com/kubevirt/kubevirt/blob/v1.9.0/pkg/storage/export/export/export.go

The `system.disk` and `exchange.disk` selectors cannot collide with normal data names (dots are invalid in data disk names). CDI-managed system and block exchange images are exported as raw images, not guest-filesystem snapshots. VirtioFS is not a raw disk; its published files remain individually downloadable through the bounded file API. Test coverage additionally streams the system and block exchange exports and validates length, source-specific filename and digest. Hosted native export passed on the qualified commit; do not extend that result to untested storage classes or guest profiles.

## Published VirtioFS file bundle

GET `/computers/{id}/exchange-bundle` on a converged halted VM returns an immutable TAR containing only supported flat published inputs and completed, checksum-verified outputs plus a per-entry SHA256 manifest. It rejects incomplete publications, symlinks, hardlinks, oversized data and directory/count overflow instead of silently truncating. Maximum 32 MiB archive and 64 files. The API serializes capture with VM lifecycle and upload operations; the broker constructs the complete bounded archive before responding. This is not a recursive backup of arbitrary guest directories, not a full storage snapshot, and not a restore API. The raw `exchange.disk` selector is refused for VirtioFS. No additional Kubernetes privilege is required.

The `X-VM-Export-Bytes` response header is the validated native payload byte count, independently of HTTP transfer framing. Clients must reject missing or inconsistent counts and truncated or oversized streams. `Content-Length`, when present, must agree; a client may receive chunked framing instead.
