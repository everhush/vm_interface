# API quickstart and integration guide

The service exposes REST under `/api/v1` and scoped WebSocket connections on the TLS gateway. The live OpenAPI 3.1 document is the authoritative contract: `GET /api/v1/openapi.json`. `GET /api/v1/schema` and `/schema/advanced` expose allowed configurations; `/capabilities` distinguishes implementation and unsupported profiles.

## Evaluation prerequisites

Use an already deployed **disposable** environment from the [device guide](device-validation.md). The examples require a valid operator-issued test identity or appropriately scoped account API key in `VM_TOKEN`; this is not production authentication. Keep the HTTP service bound to loopback. Use a trusted CA for TLS WSS; never disable certificate verification. Do not persist tokens, display tickets or network grants in history, evidence or source.

```sh
# Use Bash on the dedicated disposable device, with the API port-forward running.
export API_URL=http://127.0.0.1:3000/api/v1
set +x
if [ -z "${VM_TOKEN:-}" ]; then
  read -r -s -p 'Evaluation bearer token: ' VM_TOKEN; printf '\n'
fi
curl --fail -H "Authorization: Bearer $VM_TOKEN" "$API_URL/account"
curl --fail -H "Authorization: Bearer $VM_TOKEN" "$API_URL/account/quota"
curl --fail -H "Authorization: Bearer $VM_TOKEN" "$API_URL/images"
```

If you are the operator of the locally provisioned evaluation, see [local evaluation access](device-validation.md#local-evaluation-api-access) for safe bootstrap-token handling. Use an appropriately scoped account key for a separate client. See the live `/keys` contract for creating and revoking keys.

## Example: plan a smoke VM

The following minimal CirrOS profile is the exact shape used by the native smoke client. It is a test profile, not a persistent desktop or a production OS image.

```sh
VM_SPEC=$(mktemp)
cat > "$VM_SPEC" <<'JSON'
{"version":1,"name":"example-smoke","architecture":"amd64","cpu":1,"memoryMiB":512,"image":"cirros-smoke"}
JSON
curl --fail -X POST -H "Authorization: Bearer $VM_TOKEN" \
  -H 'Content-Type: application/json' --data-binary @"$VM_SPEC" \
  "$API_URL/computers/plan"
```

Planning validates configuration and quota without creating a computer. To create a halted VM, submit the same JSON to `POST /computers` with a unique `Idempotency-Key` (e.g. generated by `openssl rand -hex 16`). The returned `result.id` is the computer ID; save the operation receipt. Inspect `GET /computers/{id}` and `GET /operations/{id}` until observed state converges. Then POST `/computers/{id}/start` with a new idempotency key. Inspect VMI status and actual guest display, not just submission. Stop using `POST /computers/{id}/stop`. Delete only an owned disposable computer; for a computer with persistent disks, `DELETE /computers/{id}?deleteDisks=true` requires explicit authorization and destroys its managed disks. Do not add the flag by default.

For a reproducible executable client including ownership and cleanup assertions see [scripts/e2e-smoke.ts](../scripts/e2e-smoke.ts). Use [the functional proof client](../scripts/e2e-api-functional-proof.ts) for persistent Fedora software execution, guest exchange, pointer proof, archive and recording.

## Walkthrough: create and operate a smoke VM

Continue from the successful plan example above, using the same Bash session, `VM_SPEC` and account token. This is an interactive walkthrough for a **disposable** evaluation, not a deployment script. It creates an ephemeral CirrOS smoke computer, not a persistent workstation. You need curl, Node.js 24 and OpenSSL. Do not run steps blindly: inspect the receipt and observed VM state at each checkpoint. Use the same account for the full walkthrough.

**Create.** Use the spec from the plan example. Keep the original key in this session for receipt recovery.

```sh
CREATE_KEY=$(openssl rand -hex 16)
CREATED=$(curl --fail-with-body --silent --show-error -X POST \
  -H "Authorization: Bearer $VM_TOKEN" \
  -H "Idempotency-Key: $CREATE_KEY" -H 'Content-Type: application/json' \
  --data-binary @"$VM_SPEC" "$API_URL/computers")
```

Only if creation returned successfully, extract and inspect the receipt below. If the connection failed or the outcome is uncertain, recover by `CREATE_KEY` using the receipt lookup described below; do not generate a replacement key.

```sh
printf '%s\n' "$CREATED"
VM_ID=$(printf '%s' "$CREATED" | node -e 'console.log(JSON.parse(require("node:fs").readFileSync(0)).result.id)')
OP_ID=$(printf '%s' "$CREATED" | node -e 'console.log(JSON.parse(require("node:fs").readFileSync(0)).operationId)')
curl --fail -H "Authorization: Bearer $VM_TOKEN" "$API_URL/operations/$OP_ID"
curl --fail -H "Authorization: Bearer $VM_TOKEN" "$API_URL/computers/$VM_ID"
```

**Start and observe.** Once creation is observed and the computer is halted, submit a new operation with a fresh key.

```sh
START_KEY=$(openssl rand -hex 16)
curl --fail -X POST -H "Authorization: Bearer $VM_TOKEN" \
  -H "Idempotency-Key: $START_KEY" -H 'Content-Type: application/json' \
  --data '{}' "$API_URL/computers/$VM_ID/start"
curl --fail -H "Authorization: Bearer $VM_TOKEN" "$API_URL/computers/$VM_ID"
```

Repeat the last GET at a reasonable interval until `instance.status.phase` is `Running`. This is infrastructure state, not proof of guest login. After boot, inspect the actual display using the owned account authorization:

```sh
SCREENSHOT=$(mktemp --suffix=.png)
curl --fail --silent --show-error -H "Authorization: Bearer $VM_TOKEN" \
  --output "$SCREENSHOT" "$API_URL/computers/$VM_ID/screenshot"
printf 'Screenshot saved privately at %s\n' "$SCREENSHOT"
```

Open the PNG locally; treat it as private guest data. For RFB viewing and input ownership use the scoped ticket and lease routes in OpenAPI, not raw Kubernetes access.

**Stop and clean up.** Stop the computer and inspect its state until the instance is absent and the desired run strategy is `Halted`. Only then delete this disposable smoke VM.

```sh
STOP_KEY=$(openssl rand -hex 16)
curl --fail -X POST -H "Authorization: Bearer $VM_TOKEN" \
  -H "Idempotency-Key: $STOP_KEY" -H 'Content-Type: application/json' \
  --data '{}' "$API_URL/computers/$VM_ID/stop"
curl --fail -H "Authorization: Bearer $VM_TOKEN" "$API_URL/computers/$VM_ID"
```

Repeat the state GET until `instance` is null and `desired.runStrategy` is `Halted`. Do not proceed merely because stop returned a receipt. After observing the stopped state, run the next block only for this disposable smoke computer:

```sh
DELETE_KEY=$(openssl rand -hex 16)
curl --fail -X DELETE -H "Authorization: Bearer $VM_TOKEN" \
  -H "Idempotency-Key: $DELETE_KEY" "$API_URL/computers/$VM_ID"
curl --fail -H "Authorization: Bearer $VM_TOKEN" "$API_URL/account/quota"
```

Confirm deletion by observing the computer is absent from the account list and its reservation released. Quota can include other owned computers. Never add `deleteDisks=true` to a persistent VM deletion without deliberate authorization and backup review. When finished, unset `VM_TOKEN`, remove the temporary spec with `rm -f -- "$VM_SPEC"`, and securely remove or retain the private screenshot according to the operator's policy. Stop the port-forward; the dedicated cluster and test identity remain the operator's responsibility.

**If a mutation disconnects:** do not run the next step or create a replacement key. For example, recover the original start receipt with:

```sh
curl --fail -H "Authorization: Bearer $VM_TOKEN" \
  -H "Idempotency-Key: $START_KEY" "$API_URL/operations/by-key"
```

For an uncertain create, stop or delete, substitute the corresponding original `CREATE_KEY`, `STOP_KEY` or `DELETE_KEY` instead of `START_KEY`. Use the actual receipt and resource state to determine what happened. The executable [smoke test](../scripts/e2e-smoke.ts) is the reference for observed lifecycle, bounded waits, cleanup and rejection behavior. This walkthrough is documentation of the existing contract; the exact hosted tests, not this example alone, establish qualification.

## Route groups

All paths below are relative to `/api/v1`.

| Group | Representative endpoints |
| --- | --- |
| Discovery | `GET /health`, `/openapi.json`, `/schema`, `/schema/advanced`, `/images`, `/capabilities` |
| Identity | `/account`, `/account/quota`, `/keys`, `/audit` |
| Lifecycle | `/computers/plan`, `/computers`, `/computers/{id}/{start,stop,restart,reset}` |
| Desired configuration | `/computers/{id}/hardware`, `/boot`, `/storage`, `/disks` (plan endpoints where applicable) |
| Media | `/media-artifacts`, `/computers/{id}/media/{slot}`, `/chunks`, `/commit`, `/artifact` |
| Storage export | `/computers/{id}/disk-exports/{name}` and `/file`; see [disk exports](disk-export.md) |
| Exchange | `/computers/{id}/files`, `/files/{name}`, `/exchange-bundle` |
| Display and input | `/computers/{id}/console-tickets`, `/screenshot`, `/vnc`, `/input-lease`, `/input` |
| Recordings | `/computers/{id}/recordings`, recording-specific `/stop`, `/file` |
| Private TCP | `/computers/{id}/exposures`, grant-specific `/connect` |
| Durable receipts | `/operations`, `/operations/{id}`, `/operations/by-key` |

Use the complete OpenAPI paths and request schemas instead of treating the grouped notation as literal URL syntax. Binary upload endpoints use declared SHA-256/size constraints; the resumable media path uses `Upload-Offset` and `X-Content-SHA256`. Registered media remains account-owned. Never upload unlicensed media or secrets to example VMs.

## Semantics and safety

- A `202` receipt is submission, not completion. Poll owned state and operation observations. On timeout, read `/operations/by-key` with the original idempotency key and inspect target state; do not blindly replay uncertain mutations. Reuse the same key only for the same intended operation under the documented recovery rules.
- Cold hardware/storage operations require stopped, converged state and optimistic resource versions where applicable. Shrink and unsupported profiles are rejected. Storage growth does not certify guest partition/filesystem growth.
- A `Console` authorization ticket is scoped to a VM and purpose (screenshot/observe/control); a control lease is required for input. Human takeover revokes automation authority. Screenshot and recording are sensitive guest data; obtain consent.
- A `Network` grant is private, expiring and scoped to a guest TCP endpoint. It cannot provide Kubernetes, raw host or unrelated VM access. Use authenticated TLS WSS.
- Treat `401/403/404/409/413/422/429/502` according to the actual response and contract; do not retry destructive writes automatically. Keep traces redacted and preserve error evidence.
